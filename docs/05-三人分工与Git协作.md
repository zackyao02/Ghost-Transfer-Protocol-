# 三人分工与 Git 协作

## 1. 分工原则

- A 是场景唯一维护者。
- B 交付角色、VFX、音频 Prefab，不直接写战斗逻辑。
- C 是代码、输入、构建和最终集成负责人。
- Lead 负责冻结范围、验收和合并优先级，不另建第二套主线。

## 2. 成员 A：场景、关卡与环境美术

**分支：**`feature/scene`

负责：

- 废弃神社灰盒与最终场景。
- 祭坛、神龛、Boss 出场口和固定镜头节点。
- 灯光、雾、雨、城市远景和场景后处理。
- 五幕流程的空间切换与环境变化。
- 封存、共生、换壳对应的场景伤痕表现。
- 接收 B 的 Prefab 并放入主场景。

首个交付：

- 可运行灰盒场景。
- 五个镜头节点。
- 石精点位、Boss 点位和神降演出位置。

不得修改：

- 手势服务、技能伤害、Agent 接口和角色源资产。

## 3. 成员 B：角色、Tripo、VFX 与音效

**分支：**`feature/characters`

负责：

- Tripo 生成和整理石精、山魈、法相与三套 Ghost 义体。
- 角色材质、简单绑定与必要动画。
- 剑诀、净化符、神降、Boss 出场和死亡 VFX。
- 手势确认、技能、Boss 和结算音效。
- 向 A/C 交付独立 Prefab 与调用说明。

首个交付：

- 山魈和法相的可用 Prefab。
- 三种技能占位 VFX。
- 一套统一材质和色板样例。

不得修改：

- 主场景长期摆放、手势代码、伤害计算和流程状态机。

## 4. 成员 C：玩法、手势、Agent、UI 与集成

**分支：**`feature/input`

负责：

- Python MediaPipe 服务改造：删除 JPEG，只发 JSON。
- Unity TCP 接收、断线恢复与 `trace_id` 去重。
- `GestureInputRouter`、手势状态机和键鼠导演模式。
- 战斗、技能、Boss 状态和 GameFlowController。
- UI、动作进度、识别状态和调试面板。
- WorldStateStore 与一次 World Director Agent 决策。
- Windows 构建、稳定版维护和最终合并。

首个交付：

- 键盘可完整通关的灰盒版本。
- Python → Unity 的单个手势事件链路。
- 服务断开后 1 秒内回退键盘。

限制：

- Agent 只做一次结构化决策，不扩展为聊天系统或多 Agent。
- 不负责重做角色与环境模型。

## 5. Git 分支结构

```text
master                 稳定、可演示版本
integration/demo       每日集成与联调
feature/scene          A
feature/characters     B
feature/input          C
```

所有功能分支从最新 `master` 创建。日常成果先进入 `integration/demo`，完整试玩通过后再合入 `master`。

## 6. 提交和合并规则

- 不直接向 `master` 开发。
- 一次提交只完成一个明确功能。
- 提交信息示例：`feat(scene): 完成祭坛灰盒与镜头节点`。
- 大模型、贴图和音频按目录交付，不随意移动他人文件。
- A 负责主场景文件；B 和 C 不直接同时修改该文件。
- B 通过 Prefab 交付；C 通过事件调用，不复制美术逻辑。
- 接口变化必须同步更新技术文档。
- 每次合并前先拉取最新 `integration/demo` 并本地运行一局。

## 7. 每日同步格式

每人只汇报四项：

```text
已完成：
当前可演示内容：
阻塞问题：
下一次交付时间：
```

若任务连续两小时没有可见成果，立即降级或切换方案。

## 8. 冲突处理

- 场景冲突：以 A 的场景为准，其他人重新挂 Prefab。
- 代码冲突：由 C 合并，禁止删除无法理解的用户改动。
- 美术表现冲突：统一遵循四色视觉规范。
- 范围冲突：只有能提高稳定性、评分或演示记忆点的功能进入 P0。
